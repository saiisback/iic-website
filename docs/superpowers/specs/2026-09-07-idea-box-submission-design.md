# Idea Box Submission Design

## Goal

Create a public `/idea-box` page where BMSIT student builders can explain what they are building, how far the prototype has progressed, and what support they need. Submissions will be validated on the server and stored durably in Neon PostgreSQL.

## Scope

This change includes:

- changing the visible homepage `Idea Box` link from `#idea-box` to `/idea-box`;
- one responsive Idea Box form page;
- one server-only submission endpoint;
- one Neon database migration and repository boundary;
- server and client validation, success feedback, and recoverable error feedback;
- automated tests plus live desktop and mobile verification.

An admin dashboard, authentication, editing submissions, file uploads, email notifications, judging, scoring, and public idea listings are outside this change.

## User Experience

The form will use the existing IIC visual language: a deep-black canvas, white editorial typography, sharp borders, and restrained emerald-teal accents. It will feel like a serious builder intake form rather than a generic survey.

The page will use a single scrolling form, divided into numbered sections:

1. **Builder identity** — full name, USN, and college email.
2. **Build brief** — project name, one-line summary, problem being solved, and a detailed description of what is being built.
3. **Prototype state** — domain, current prototype status, and team status.
4. **Support request** — support needed, optional demo or GitHub URL, and consent.

On desktop, the heading and explanatory copy will remain in a sticky left column while the form occupies the right column. On mobile, the page becomes one readable vertical column. Every field will have a visible label, supporting hint where useful, and an accessible error message.

The submit button will display a pending state while the request is in flight. A successful submission will replace the form with a confirmation panel containing the generated submission ID and a link back home. A failed submission will preserve entered values and show a concise retry message.

## Form Contract

Required fields:

- `fullName`: 2–80 characters.
- `usn`: 6–20 letters, numbers, or hyphens; normalized to uppercase.
- `email`: valid email syntax, maximum 160 characters. It is labeled as college email but no institution domain is hard-coded.
- `projectName`: 2–120 characters.
- `summary`: 10–180 characters.
- `problem`: 20–1,500 characters.
- `solution`: 20–2,500 characters; answers “What are you building?”
- `domain`: one of AI/ML, Software/SaaS, Hardware/IoT, Robotics, Sustainability, Health, Education, FinTech, or Other.
- `prototypeStatus`: one of Idea, Research, Design, Proof of Concept, Working Prototype, Testing, Pilot Ready, or Launched.
- `teamStatus`: Solo, Have a Team, or Looking for Teammates.
- `supportNeeds`: at least one of Mentorship, Technical Guidance, Funding, Lab/Tools, IP/Patent, Business Model, Teammates, or User Testing.
- `consent`: must be true.

Optional field:

- `projectUrl`: an `http` or `https` URL, maximum 500 characters.

The browser will provide immediate required-field guidance, but the server validator is authoritative. Validation failures return field-specific errors without writing to the database.

## Data Model

The migration will create `idea_submissions` with:

- `id uuid primary key` generated by the application;
- `created_at timestamptz not null default now()`;
- identity fields: `full_name`, `usn`, `email`;
- project fields: `project_name`, `summary`, `problem`, `solution`;
- classification fields: `domain`, `prototype_status`, `team_status`;
- `support_needs jsonb` containing a validated array of strings;
- nullable `project_url`;
- `consent boolean not null`;
- `review_status text not null default 'new'`.

The migration will add indexes on `created_at`, `usn`, and `review_status`. Multiple submissions from one USN are allowed because a student may submit different projects or a later iteration.

## Server Architecture

- `lib/ideas/validation.ts` owns normalization and validation as a pure, testable module.
- `lib/ideas/repository.ts` owns the parameterized Neon insert and reads `DATABASE_URL` only on the server.
- `app/api/ideas/route.ts` accepts JSON `POST` requests, rejects malformed or oversized input, invokes validation, stores valid submissions, and returns JSON.
- `components/idea-box/IdeaBoxForm.tsx` owns client-side form state, field errors, pending state, and success state.
- `app/idea-box/page.tsx` supplies static metadata and renders the page shell plus form.
- `db/migrations/001_create_idea_submissions.sql` is the explicit schema migration.

The Neon connection string must exist only in `.env.local` as `DATABASE_URL`. It must never be rendered client-side, logged, committed, or included in error responses.

## API Behavior

`POST /api/ideas` accepts the form contract as JSON.

- `201`: `{ ok: true, submissionId: string }` after a successful insert.
- `400`: `{ ok: false, error: "validation_failed", fieldErrors: Record<string, string> }`.
- `413`: `{ ok: false, error: "payload_too_large" }`.
- `500`: `{ ok: false, error: "submission_failed" }`; internal database details remain server-only.

The API uses parameterized queries. A hidden honeypot field will reject obvious automated spam without storing it. No rate-limiting service or CAPTCHA is added in this scope.

## Failure and Recovery

- Missing `DATABASE_URL` produces a controlled server error and a generic retry message in the form.
- A Neon outage or insert failure does not clear the form.
- Double submission is prevented while a request is pending.
- Invalid JSON and unsupported methods do not write data.
- A successful response clears sensitive form state and shows only the submission ID.

## Accessibility

- All controls have explicit labels and programmatic descriptions.
- Error messages are connected using `aria-describedby`; the first invalid field receives focus after a failed submission.
- Status changes use an `aria-live` region.
- Keyboard focus is visibly styled.
- Color is never the sole error indicator.
- Textareas have practical minimum heights and character limits.

## Testing

Implementation will use red-green-refactor cycles covering:

1. navigation from the homepage to `/idea-box`;
2. normalization and every server validation branch;
3. parameter mapping into the Neon repository;
4. API success, validation failure, malformed payload, oversized payload, and database failure behavior;
5. form semantics, required fields, prototype options, support options, error state, pending state, and success state;
6. production build and live desktop/mobile submission flow against the configured Neon database.

## Acceptance Criteria

- The homepage `Idea Box` link opens `/idea-box`.
- The form contains the approved identity, build, prototype, team, support, URL, and consent questions.
- Invalid submissions show actionable field-level feedback and are not stored.
- Valid submissions create one Neon row and display its generated submission ID.
- Database errors preserve the form and do not expose secrets or SQL details.
- The page is usable by keyboard and at desktop and mobile widths.
- Tests, lint, and production build pass.
